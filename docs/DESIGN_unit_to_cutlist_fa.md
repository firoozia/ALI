# سند طراحی — ماژول «یونیت → لیست قطعه → خروجی CSV» (FIROO CAM)

> هدف این سند: نقشه‌ی کاملِ بخشِ جدیدِ نرم‌افزار تو، بر پایه‌ی تحلیلِ سه مرجع
> (CutClick، Cabinet Pro، WoodworkingShop) و نیازهایی که مشخص کردی. این سند
> «طراحی» است، نه کد؛ برای بررسی و اصلاح توست. وقتی تأیید کردی، پیاده‌سازی می‌کنیم.

---

## ۱. هدف و ارزش محصول

کاربر (کابینت‌ساز/فروشنده) **نباید دستی یونیت‌ها را به قطعه بشکند**. کار اپ:

```
کتابخانه‌ی مدل ──► انتخاب مدل ──► ویرایش پارامتر ──► تولید خودکار قطعه‌ها
      │                                                     │
   قطعه‌ی دستی ───────────────────────────────────────────┤
                                                            ▼
                               لیستِ کلیِ پروژه (همه‌چیز تا لحظه‌ی خروجی قابل ویرایش)
                                                            ▼
                                   روسازی (نوار + شیار + متریال + الیاف)
                                                            ▼
                                        ✅ خروجی CSV  ──►  زیناکس
                                 (نست، جی‌کد، لیبل و … همه در زیناکس)
```

**مرز مسئولیت:** هرچه بعد از CSV است (نست/بهینه‌سازی برش، G-code، لیبل، نقشه‌ی
برش، ارتباط با دستگاه) کارِ **زیناکس** است. این اپ فقط «تولید لیست قطعه‌ی دقیق و
قابل‌ویرایش و خروجی تمیز» را انجام می‌دهد. پس **مهم‌ترین خروجی = CSV** که زیناکس
بتواند import کند (یا اپراتور از رویش دستی وارد کند).

**تمایز نسبت به Cabinet Pro و بقیه:** هر دو مرجع، قطعه را می‌سازند ولی **نوار و
شیار را در اندازه‌ی واقعیِ برش اعمال نمی‌کنند**. مزیت تو دقیقاً همین‌جاست:
`اندازه‌ی برش = اندازه‌ی نهایی − مجموع ضخامت نوارِ آن ضلع` و شیار واقعاً روی ابعاد
اثر بگذارد.

## ۲. کتابخانه‌ی مدل (Model Library)

قلب اپ. مجموعه‌ای از «مدل»های آماده که کاربر انتخاب و ویرایش می‌کند.

### مدل چیست؟
یک **قالب پارامتریک**: چند بُعد با نام + فهرست قطعه‌ها که طول/عرض/تعدادشان
**فرمولِ** آن بُعدهاست. (ایده از CutClick: فرمول رشته‌ای؛ ولی ما فرمول‌ها را
**داخلی و درست و قابل‌اعتماد** می‌نویسیم، نه از سرور.)

### دسته‌بندی پیشنهادی مدل‌ها
- **کابینت زمینی** (Base): تک‌درب، دودرب، کشودار (۲/۳/۴ کشو)، گازوری، سینک.
- **کابینت دیواری** (Wall): تک‌درب، دودرب، بازشو، آبچکان.
- **کمد/یونیت بلند** (Tall): کمد لباس، یونیت فر/مایکروویو.
- **اجزای آزاد**: طبقه‌ی اضافه، جاکفشی، دراور مستقل.
- **یونیت خام/سفارشی**: کاربر صفر شروع می‌کند و قطعه‌ی دستی می‌زند.

### ذخیره‌سازی
هر مدل یک فایل **JSON** در پوشه‌ی `models/` (مثل `designs/` فعلی‌ات). ساختار:

```jsonc
{
  "id": "base_2door",
  "name": {"fa": "کابینت زمینی دو درب", "en": "Base 2-Door"},
  "category": "base",
  "params": {                      // پارامترهای قابل‌ویرایشِ کاربر + پیش‌فرض
    "W": 800, "H": 720, "D": 560,
    "doors": 2, "shelves": 1, "drawers": 0,
    "back_inset": true             // پشت‌بند تورفته یا روکوب
  },
  "settings": {                    // ثابت‌های ساخت (قابل تغییر در تنظیمات)
    "t": 18,                       // ضخامت ورق بدنه
    "back_t": 3,                   // ضخامت پشت‌بند
    "door_gap": 3,                 // درز بین/دور درب (reveal)
    "groove_depth": 8,             // عمق شیار پشت‌بند
    "groove_setback": 10           // فاصله‌ی شیار از لبه
  },
  "parts": [                       // فرمولِ هر قطعه
    {"name":"بدنه","type":"side","L":"H","W":"D","qty":2,"material":"body","grain":"L"},
    {"name":"کف/سقف","type":"tb","L":"W-2*t","W":"D","qty":2,"material":"body","grain":"L"},
    {"name":"طبقه","type":"shelf","L":"W-2*t","W":"D-20","qty":"shelves","material":"body","grain":"L"},
    {"name":"پشت‌بند","type":"back","L":"W-2*t+2*groove_depth","W":"H-2*t+2*groove_depth","qty":1,"material":"back","grain":"none"},
    {"name":"درب","type":"door","L":"H-2*door_gap","W":"(W-(doors+1)*door_gap)/doors","qty":"doors","material":"door","grain":"L",
      "edge":{"all":"pvc_1"}}      // روسازیِ پیش‌فرضِ این قطعه
  ]
}
```

کاربر می‌تواند مدل‌های خودش را بسازد/ذخیره کند (Save as). این «کتابخانه‌ی قابل‌رشد»
همان چیزی است که اپ را از رقبا جلو می‌اندازد.

## ۳. مدل داده (Data Model)

روی `data_models.Part` فعلیِ تو سوار می‌شویم و فقط چند فیلدِ روسازی اضافه می‌کنیم،
تا با nesting/CSV موجود سازگار بماند.

### `Unit` (جدید)
| فیلد | معنی |
|---|---|
| `unit_id` | شناسه |
| `model_id` | کدام مدلِ کتابخانه |
| `name` | نام یونیت (مثلاً «کابینت زیر سینک») |
| `params` | مقادیر ویرایش‌شده‌ی کاربر (W/H/D/تعداد…) |
| `qty` | تعداد تکرارِ این یونیت |
| `parts` | قطعه‌های تولیدشده (کَش؛ با ویرایش پارامtersها دوباره ساخته می‌شود) |

### `Part` (گسترش مدل فعلی)
فیلدهای فعلی می‌مانند: `part_code, width, height, thickness, material, label,
grain…`. این‌ها اضافه می‌شوند (همه با پیش‌فرض، تا کدِ فعلی نشکند):

| فیلد جدید | نوع | معنی |
|---|---|---|
| `unit_id` | str | به کدام یونیت تعلق دارد (خالی = قطعه‌ی دستی) |
| `part_type` | str | side/tb/shelf/back/door/drawer_* / custom |
| `qty` | int | تعداد (الان در ردیف‌ها مدیریت می‌شود؛ صریح‌ترش می‌کنیم) |
| `grain` | str | `L`=راه‌دار طول، `W`=راه‌دار عرض، `none`=ساده |
| `edge` | dict | نوار هر لبه: `{"top":code,"bottom":code,"left":code,"right":code}` |
| `groove` | list | شیارها: هرکدام `{edge, depth, setback, width}` |
| `is_finished_size` | bool | ابعاد واردشده «نهایی»‌اند یا «برش»؟ (پیش‌فرض نهایی) |
| `note` | str | توضیح قطعه |

> سازگاری: چون `edge/groove` پیش‌فرضِ خالی دارند، قطعه‌ی بدونِ روسازی دقیقاً مثل
> الان رفتار می‌کند و وارد nesting/CSV فعلی می‌شود.

### `EdgeBand` / `Material` (کاتالوگ)
- **نوار**: فهرستی با `{code, name, thickness}` — از `edge-profile.ts` واقعیِ
  WoodworkingShop الگو گرفته: PVC اتویی ۰.۴، فورنیر ۰.۶، ABS سه‌میل، لبه‌چوب ۲۰.
- **متریال/ورق**: از `sheet_library.json` فعلیِ تو گسترش می‌یابد: `{name, thickness,
  grain, default_sheet_w, default_sheet_h}`.

## ۴. فرمول‌های تولید قطعه (موتور)

روشِ ساخت = **فریم‌لس/یورو** (همان مدلِ تأییدشده‌ی Cabinet Pro، که در بازار ایران
استاندارد است). همه‌چیز میلی‌متر. نمادها: `W`=عرض، `H`=ارتفاع، `D`=عمق،
`t`=ضخامت بدنه، `bt`=ضخامت پشت‌بند، `g`=درز درب.

```
بدنه (۲)            L=H            W=D
کف و سقف (۲)         L=W-2t         W=D
طبقه (n)            L=W-2t         W=D-عقب‌نشینی(پیش‌فرض ۲۰)
واداری/تقسیم        L=D-عقب‌نشینی   W=فاصله‌ی داخلیِ عمودی
پشت‌بند روکوب        L=W            W=H                 (روی بدنه)
پشت‌بند شیاری        L=W-2t+2*عمق‌شیار   W=H-2t+2*عمق‌شیار   (داخل شیار)
درب (تک)            L=H-2g         W=W-2g
درب (دوقلو، d عدد)   L=H-2g         W=(W-(d+1)*g)/d
کشو جلو/عقب         L=دهانه-۲۶-۲t   (۲۶ لقیِ ریل)
کشو بغل             L=D-۵۰
ارتفاع هر کشو        =(ارتفاع‌دهانه-(n+1)*۲۵)/n
کف کشو              =(دهانه-۲۶) × (D-۵۰)
```

> همه‌ی عددهای ثابت (۲۰، ۲۶، ۵۰، ۲۵، درز، عمق‌شیار) **پارامترِ قابل‌تنظیم**اند، نه
> هارد‌کد — چون روش هر کارگاه فرق دارد. (درسِ گرفته‌شده از هر سه مرجع.)

### ارزیاب فرمول
یک ارزیابِ امنِ ساده (نه `eval` پایتون): `+ - * / ( )` و توکن‌های پارامتر. تقسیم بر
صفر → خطای واضح (نه صفرِ بی‌صدا؛ این باگِ CutClick بود). هر فرمول قبل از استفاده
اعتبارسنجی می‌شود.

## ۵. روسازی (نوار و شیار) — تمایز اصلی

### نوار (Edge banding)
- برای هر قطعه، ۴ لبه جدا: هرکدام یک کُدِ نوار یا خالی.
- **اثر روی اندازه‌ی برش** (کاری که هیچ‌کدام از مراجع نمی‌کردند):
  ```
  اگر is_finished_size و قطعه پیش‌فرز نشده:
     عرضِ برش = عرضِ نهایی − (ضخامت نوارِ چپ + ضخامت نوارِ راست)
     طولِ برش = طولِ نهایی − (ضخامت نوارِ بالا + ضخامت نوارِ پایین)
  ```
- خروجی: علاوه بر سایزِ برش، **طول کلِ نوار به تفکیک نوع** (برای سفارش نوار) هم
  محاسبه و در گزارش می‌آید.

### شیار (Groove/Dado)
- برای پشت‌بند و کف کشو. هر شیار: `{لبه، عمق، فاصله از لبه، عرض}`.
- اثر: پشت‌بندِ شیاری بزرگ‌تر می‌شود (`+2*عمق` در هر بُعدِ شیارخورده) — در فرمول‌های
  بالا لحاظ شده.
- عرض شیار پیش‌فرض = ضخامت پشت‌بند؛ عمق پیش‌فرض ≈ نصف ضخامت بدنه (قابل‌تنظیم).

### الیاف
`L/W/none` روی هر قطعه؛ در CSV می‌رود تا زیناکس هنگام نست رعایت کند.

## ۶. جریان کاربر (Workflow) — «همه‌چیز تا خروجی قابل‌ویرایش»

```
۱) صفحه‌ی پروژه: نام مشتری/سفارش، ورق‌ها و متریال‌های پیش‌فرض
۲) تبِ یونیت‌ها:
     + افزودن یونیت → انتخاب از کتابخانه‌ی مدل → ویرایش W/H/D/تعداد درب‌و‌کشو
       → پیش‌نمایش قطعه‌ها → «افزودن به لیست»
     ویرایش/حذف/کپیِ هر یونیت در هر زمان (دوباره‌سازیِ خودکارِ قطعه‌ها)
۳) تبِ قطعه‌ی دستی: افزودن قطعه‌ی تکیِ دستی (برای چیزهای خارج از مدل)
۴) تبِ روسازی: انتخاب چندتایی قطعه → نوار ۴ لبه + شیار + متریال + الیاف
۵) تبِ لیست کل (Cut List): جدولِ همه‌ی قطعه‌ها (از همه‌ی یونیت‌ها + دستی‌ها)
     - قابل ویرایشِ درجا (سایز، تعداد، نوار، متریال)
     - گروه‌بندیِ قطعه‌های یکسان + جمع تعداد
     - اعتبارسنجی: قطعه‌ی بزرگ‌تر از ورق، مقدار منفی، فرمول خراب → هشدار
۶) دکمه‌ی خروجی: CSV (+ اختیاری PDF گزارش) → تحویل به زیناکس
```

نکته‌ی مهمی که گفتی: **قبل از پروسه‌ی خروجی، همه‌ی حالت‌ها باید قابل ویرایش باشند.**
→ معماری «لیست کل» این را تضمین می‌کند: قطعه‌ها از یونیت تولید می‌شوند ولی در لیست
کل همه مستقل و ویرایش‌پذیرند، و خروجی فقط از «لیست کل» گرفته می‌شود.

## ۷. خروجی CSV (مهم‌ترین بخش) ⭐

چون زیناکس بقیه را انجام می‌دهد، CSV باید **دقیقاً مطابق ورودیِ زیناکس** باشد.
با `csv_handler.py` فعلیِ تو هم‌راستا طراحی شده (همان ستون‌ها + ستون‌های روسازی).

### ساختار پیشنهادی (ستون‌ها قابل‌تنظیم برای تطبیق با زیناکس)
```
PartCode, PartName, Unit, Qty, Width, Height, Thickness, Material, Grain,
Edge_Top, Edge_Bottom, Edge_Left, Edge_Right, Groove, Label, Note
```
- `Width/Height` = **اندازه‌ی برش** (بعد از کسر نوار)؛ یک گزینه برای خروجیِ
  «اندازه‌ی نهایی» هم می‌گذاریم.
- `Grain` = L/W/none.
- `Edge_*` = کد/نوعِ نوارِ هر لبه (یا خالی).
- جداکننده (`,` یا `;`) و ترتیب/نام ستون‌ها **در تنظیمات قابل تغییر**، چون
  نرم‌افزارهای مقصد سخت‌گیرند (درسِ گرفته‌شده از تحقیق: OptiCut حداقل ۶ ستون
  می‌خواهد، PolyBoard کاملاً configurable است).

### ‼️ تنها چیزی که از تو لازم دارم
**یک نمونه فایل ورودیِ زیناکس** (همان CSV/Excel که زیناکس import می‌کند). با آن،
ستون‌ها را دقیقاً مطابقش قفل می‌کنم. اگر نمونه نداری، همین ساختار بالا را به‌عنوان
پیش‌فرض می‌گذاریم و بعداً تطبیق می‌دهیم.

> خروجی‌های جانبیِ اختیاری (بعد از MVP): CSV سازگار با OptiCut، و یک PDF گزارشِ
> لیست قطعه + طول نوار. **G-code/DXF/نست لازم نیست** (کارِ زیناکس).

## ۸. جایگاه در کد تو (Integration)

- اپ فعلی PySide6 با تب‌های Parts/Sheet/Nesting/Export است. این ماژول چند تبِ
  جدید اضافه می‌کند: **Models/Units**، **Surfacing**، و استفاده از **Cut List/Export**.
- ماژول‌های پایتونیِ جدید (بدون وابستگی به هیچ اپ خارجی):
  ```
  cabinet/
    model.py          # بارگذاری/ذخیره‌ی مدل‌های JSON
    formula.py        # ارزیاب امن فرمول + اعتبارسنجی
    generator.py      # یونیت(params) → List[Part]
    surfacing.py      # نوار/شیار + کسر اندازه‌ی برش + جمع طول نوار
  catalog/
    edgebands.json    # کاتالوگ نوار (از WoodworkingShop الگو)
    models/*.json     # کتابخانه‌ی مدل‌ها
  export/
    csv_zinax.py      # خروجی CSV مطابق زیناکس (configurable)
  ```
- از موجودی‌های فعلی استفاده‌ی مجدد: `data_models.Part` (گسترش)، `csv_handler`
  (ستون‌ها/aliasها)، `config.json` (تنظیمات ساخت)، `locales/` (fa/ar/en).
- مجوزها: از منطقِ WoodworkingShop فقط **ایده/فرمول/ثابت‌ها** را بازنویسی می‌کنیم
  (MIT، آزاد با ذکر منبع)؛ از CutClick و Cabinet Pro فقط **ایده‌ی طراحی** (کپی کد
  نمی‌کنیم).

## ۹. فازبندی پیشنهادی

- **فاز ۱ (MVP):** مدل داده + ارزیاب فرمول + ۳ مدلِ پایه (زمینی تک/دودرب، دیواری) +
  تولید قطعه + لیست کل قابل‌ویرایش + **خروجی CSV**. (قطعه‌ی دستی هم همین‌جا.)
- **فاز ۲:** روسازیِ کامل (نوار ۴ لبه با کسر اندازه + شیار) + جمع طول نوار + کتابخانه‌ی
  بزرگ‌ترِ مدل‌ها + Save-as مدل کاربر.
- **فاز ۳:** کشودار و بلند/کمد + PDF گزارش + خروجی OptiCut + چندزبانه‌ی کامل.
- **فاز ۴:** پیش‌نمایش ساده‌ی ۲بعدی/۳بعدیِ یونیت (اختیاری).

## ۱۰. تصمیم‌هایی که باید تأیید/مشخص کنی

1. **نمونه‌ی CSV ورودیِ زیناکس** (مهم‌ترین) — برای قفل‌کردن ستون‌ها.
2. روش ساختِ پیش‌فرض: فریم‌لس تأیید است؟ face-frame هم لازم داری؟
3. واحد ورودی کاربر: cm+mm (مثل CutClick/Cabinet Pro) یا فقط mm؟
4. اولین مدل‌هایی که بیشترین استفاده را داری (تا فاز ۱ را دقیقاً رویشان بسازیم).
5. واحد پول/قیمت لازم است در این اپ یا فقط سایز؟ (گفتی فقط سایز — تأیید می‌کنی؟)
