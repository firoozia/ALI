# طراحی نسخه ۲ — تمرکز روی طراحی یونیت، کتابخانه‌ی متریال، و خروجی‌ها

> مکملِ `DESIGN_unit_to_cutlist_fa.md` و `zinax_export_mapping_fa.md`.
> بر پایه‌ی نیازهای تازه‌ات: تمرکزِ اصلیِ اپ روی **طراحی و ویرایشِ قدرتمندِ یونیت**
> باشد؛ کتابخانه‌ی رنگ/ضخامت/MDF داشته باشیم؛ انتخابِ ورق حتی در زیناکس هم ورق
> بسازد؛ خروجی = CSV کامل + خلاصه + «دلیل»؛ و چون روش‌های ساختِ یونیت متنوع‌اند،
> دستِ ما در ویرایش باز باشد.

## ۱. جمله‌ی محوری
> اپ باید طوری یونیت را طراحی و قطعه‌ها را دربیاورد که وقتی فایل در زیناکس آپلود شد،
> زیناکس **فقط مراحل بعدی** (نست، جی‌کد، لیبل) را انجام دهد و هیچ چیزی برای تعریف‌کردن
> باقی نماند. پس همه‌ی هوشِ «چه قطعه‌ای، با چه سایز، چه ورق، چه رنگ، چه ضخامت» سمتِ ماست.

---

## ۲. روش‌های ساختِ یونیت (پشت‌بندِ ۶ میل) — مدلِ قابل‌تنظیم

کاربرها پشت‌بند را متفاوت می‌سازند. به‌جای یک روشِ ثابت، یک **«روش ساخت»** برای هر
یونیت (یا پیش‌فرضِ کارگاه) می‌گذاریم. سه حالتِ اصلی:

> **پیش‌فرضِ اپ = روشِ شیاری (ب).** استانداردِ جهانی همین است — شیار می‌زنند و
> فیبر/MDF را با **هر ضخامتی** داخلش می‌گذارند؛ بیشترِ نرم‌افزارها هم همین‌طور حساب
> می‌کنند. دو روشِ دیگر (منگنه، بیرون) فقط گزینه‌اند. روشِ دیگری غیر از این سه نداریم.

### الف) منگنه پشت کار (applied / overlay)
پشت‌بند روی لبه‌ی عقبِ بدنه منگنه می‌شود.
```
پشت‌بند:  طول = W            عرض = H          (کلِ بیرونِ کابینت)
بدنه/کف/سقف: بدون تغییر
عمقِ قابل‌استفاده: کامل
```
- در CSV: پشت‌بند یک ردیفِ جدا با `mdf_thickness_mm = 6` و رنگ/متریالِ خودش.
- نیاز به شیار ندارد.

### ب) شیاری (grooved) — ✅ پیش‌فرض و استانداردِ جهانی
در بدنه/کف/سقف یک شیار با عمق `dg` و فاصله‌ی `s` از عقب زده می‌شود؛ فیبر/MDF (با هر
ضخامتی) داخل شیار می‌نشیند. عرضِ شیار = ضخامتِ همان فیبر.
```
پشت‌بند:  طول = (W − 2t) + 2*dg      عرض = (H − 2t) + 2*dg
بدنه/کف/سقف: علامتِ شیار روی لبه‌ی مربوطه  → در CSV سلولِ لبه = "S"
عمقِ قابل‌استفاده: کمی کمتر (به‌اندازه‌ی s)
```
- منبع نجاری: عمقِ شیار معمولاً ≈ نصفِ ضخامتِ بدنه؛ عرضِ شیار = ضخامتِ پشت‌بند؛
  فاصله از عقب ~۱۰mm. (همه پارامترِ قابل‌تنظیم.)
- `S` در زیناکس فقط علامتِ لیبل/نقشه است (toolpath نمی‌سازد) — دقیقاً مطابق قرارداد.

### ج) MDF بیرون از برنامه (handled outside)
پشت‌بند اصلاً وارد لیستِ برش/CSV نمی‌شود (کارگاه خودش جدا می‌زند).
```
پشت‌بند: تولید نمی‌شود (فقط در «خلاصه» به‌عنوان یادداشت می‌آید)
```
- یک کلیدِ ساده: «پشت‌بند در لیست باشد؟ بله/خیر».

> این سه حالت به‌صورت `back_method ∈ {staple, groove, outside}` در مدلِ یونیت.
> اضافه‌کردنِ حالت‌های دیگر (مثلاً تخته‌کوب کامل) بعداً راحت است.

## ۳. ضخامتِ مستقلِ هر جزء
هر جزء ضخامتِ خودش را دارد (چون در CSV هم `mdf_thickness_mm` per-row است):
- **بدنه** (side/top/bottom/shelf): مثلاً ۱۶ یا ۱۸.
- **درب**: مستقل (مثلاً ۱۸ ملامین یا درب وکیوم).
- **پشت‌بند**: مثلاً ۶.
کاربر هرکدام را جدا انتخاب می‌کند؛ قابلِ override روی هر قطعه.

## ۴. ویرایشِ باز (الزامِ تو)
- هر قطعه‌ی تولیدشده کاملاً ویرایش‌پذیر: سایز، تعداد، ضخامت، رنگ، نوار، شیار، چرخش.
- روش ساخت، عمق شیار، درزها، عقب‌نشینیِ طبقه — همه پارامتر، نه هارد‌کد.
- افزودن/حذفِ قطعه‌ی دستی در هر یونیت.
- «همه‌چیز تا لحظه‌ی خروجی قابل ویرایش» (از طریقِ صفحه‌ی لیستِ کل).

---

## ۵. کتابخانه‌ی متریال (رنگ + ضخامت + MDF) و هماهنگی با زیناکس

> کتابخانه **قابل نوشتن و ویرایش** است: کاربر رنگ/ضخامت/نوار/ورق را اضافه، ویرایش و
> حذف می‌کند (یک صفحه‌ی «کتابخانه» با افزودن/ویرایش ردیف). با چند ورودیِ پیش‌فرض
> seed می‌شود — نمونه در `catalog/materials.json`.

### چه چیزهایی را نگه می‌داریم
- **رنگ‌ها**: فهرست `{code, name, type}` — مثل `MEL-W` (ملامین سفید) یا
  `WHT-001` (فیلمِ وکیومِ سفید). → می‌رود در `pvc_code` / `pvc_color`.
- **ضخامت‌ها (فقط استاندارد)**: ۳، ۶، ۱۶، ۱۸ → می‌رود در `mdf_thickness_mm`.
  (۳/۶ = فیبر/پشت‌بند، ۱۶ = بدنه، ۱۸ = درب. ضخامتِ دیگری نداریم.)
- **نوعِ متریال**: MDF، ملامین، های‌گلاس… .
- **ابعادِ ورقِ خام**: از `sheet_library.json` (مثلاً ۲۸۰۰×۲۰۷۰).
- **نوار**: کتابخانه‌ی مشترک با زیناکس (`P1/P2/P3`، ضخامت‌ها).

### «انتخابِ ورق → در زیناکس هم ساخته شود»
این خودکار اتفاق می‌افتد، چون زیناکس **ورق را از خودِ ORDER.csv می‌سازد**:
```
pvc_color = "MEL-W" ,  mdf_thickness_mm = 18
        ↓ (در زیناکس هنگام import)
   ورقِ «MEL-W 18» ساخته/استفاده می‌شود
```
(در خروجیِ واقعیِ زیناکس دیدیم: `material = "MEL-W 18"` یا `"MDF 18"`.)
پس تنها کاری که لازم است: **کتابخانه‌ی رنگ/ضخامتِ اپِ ما باید عیناً همان کدهای
زیناکس باشد** تا ورق درست ساخته شود. چون هر دو برنامه مالِ توست، یک فایلِ مشترکِ
کتابخانه (مثلاً `materials.json`) بینشان به‌اشتراک می‌گذاریم تا همیشه یکی بمانند.

> اگر بعداً خواستی، می‌توانیم یک فایلِ جانبیِ `*_Sheets` هم برای تعریفِ صریحِ ورق
> اضافه کنیم؛ ولی فعلاً از راهِ `pvc_color + thickness` ساده‌تر و کافی است.

## ۶. خروجی‌ها (سه‌تا)

### ۱) CSV کامل (فایلِ ماشین) — اجباری
دقیقاً `ORDER_CSV_V2` (همان سندِ `zinax_export_mapping_fa.md`). کامل و بی‌نقص،
برای هر دو مدل (وکیوم/ملامین)، با همه‌ی ستون‌ها.

### ۲) خلاصه (Summary)
یک گزارشِ جمع‌بندی برای کاربر/مشتری:
- تعداد کلِ قطعه‌ها، تفکیکِ وکیوم/ملامین.
- **متراژ نوار** به تفکیکِ کد نوار (با پرت).
- تفکیکِ متریال/رنگ/ضخامت و **تخمینِ تعداد ورق** (بر پایه‌ی مساحت — تخمین، چون
  نستِ دقیق کارِ زیناکس است؛ این را صریح می‌گوییم).
- تعداد درب‌ها به تفکیکِ طرح/رنگ.

### ۳) «دلیل» / تفکیکِ ساخت (Breakdown)
این همان ارزشِ اصلیِ محصول است: چون مشتری دستی آنالیز نمی‌کند، باید **ببیند چرا این
قطعه‌ها ساخته شدند** و اعتماد کند:
- برای هر یونیت → فهرستِ قطعه‌های تولیدشده، با **فرمولِ به‌کاررفته** و مقادیر
  جایگذاری‌شده (مثلاً «کف = W−2t = ۸۰۰−۳۶ = ۷۶۴»).
- روش ساختِ انتخاب‌شده (منگنه/شیار/بیرون) و اثرش.
- هر override یا قطعه‌ی دستی مشخص شود.
- خروجی: PDF یا HTML قابلِ‌چاپ/اشتراک.

## ۷. ساختارِ داده‌ی به‌روزشده (خلاصه)

```jsonc
Unit {
  model_id, name, qty,
  params: { W, H, D, doors, shelves, drawers, ... },
  build: {                      // روش ساخت و ثابت‌ها
    back_method: "groove|staple|outside",  // پیش‌فرض: groove (استاندارد جهانی)
    groove_depth, groove_setback, back_in_list: true,
    body_t: 18, door_t: 18, back_t: 6,
    door_gap, shelf_setback
  },
  material: {                   // از کتابخانه
    body: {color_code, color_name, type},
    door: {color_code, ...},
    back: {color_code, ...}
  }
}
Part {  // علاوه بر فیلدهای قبلی
  unit_id, part_type, qty, thickness,
  color_code, color_name,       // → pvc_code / pvc_color
  grain, rotation,
  edge: {e1,e2,e3,e4},          // N | P1 | S | S/P1
  product_type: "melamine|vacuum_door",
  formula_trace: "کف = W-2t = 764"   // برای گزارشِ «دلیل»
}
```

## ۸. تمرکزِ توسعه (اولویت)
۱. **موتور طراحی یونیت** قوی و پارامتریک + سه روشِ پشت‌بند + ضخامتِ مستقلِ اجزا.
۲. **کتابخانه‌ی متریال** (رنگ/ضخامت/MDF/نوار) مشترک با زیناکس.
۳. **لیستِ کلِ کاملاً ویرایش‌پذیر**.
۴. **خروجی‌ها**: ORDER_CSV_V2 + خلاصه + دلیل.
۵. نست/جی‌کد/لیبل = **هیچ‌کدام** (کارِ زیناکس).

## ۹. تصمیم‌هایی که باید مشخص کنی
1. فهرستِ رنگ‌های واقعی‌ات (کدها) — تا کتابخانه را دقیق پر کنیم و با زیناکس یکی شود.
2. ضخامت‌های رایجت (بدنه/درب/پشت‌بند).
3. روش‌های ساختِ دیگری غیر از این سه که لازم داری؟
4. «دلیل» را PDF می‌خواهی یا HTML (یا هر دو)؟
5. فایلِ کتابخانه‌ی مشترک (`materials.json`) را کجا بگذاریم تا هم اپ لیست‌ساز هم
   زیناکس بخوانند؟ (پیشنهاد: در مخزنِ زیناکس، و اپ لیست‌ساز از همان بخواند.)
